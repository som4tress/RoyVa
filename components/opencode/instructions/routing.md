# Shared routing and learning
Model-neutral source of truth: ~/.config/opencode/routing-policy.json. Text starts with local Qwen; explicit cloud selection is respected. General local budget is 60 seconds including tools; HA local budget is 42 seconds with a 45-second target. Predictive handoff can switch earlier. Cloud continues unfinished work with its own fresh 120-second request budget. The overall response target is soft, not a hard abort. Preserve completed tool results; never replay uncertain writes. Images/video use the local vision endpoint; sampled frames omit audio and cannot prove complete event coverage.
These shared server hooks apply to Telegram, browser, terminal and ACP/Shellular. Task/procedure memories are model-independent methods, not cached live answers or weight training. Resolve current targets/parameters, authorization and fresh data on reuse. Certified typed adapters may execute validated repeats; arbitrary recorded shell commands remain advisory. Runtime evidence alone determines provider, cache hits, cost and execution success. Do not invent guarantees or figures.
Before modifying routing, learning or the bridge read ~/llm-server/cache-stress-100/HANDOFF.md and the current implementation. Preserve user changes and credentials. Older free-first/cloud-first notes are superseded by routing-policy.json. Detailed historical routing reference: /home/somdutta/llm-server/clean-context-20261103/routing.full-reference.md.

Learning consent: do not autonomously draft, generate, or register a reusable tool/skill from a response or execution trace before explicit user confirmation for that exact answer. Telegram 👍 (including the Accept & learn button) and /feedback accept are that confirmation; rejection/withdrawal revokes consent. The authoritative feedback ledger is ~/.local/share/agent-learning/. Acceptance permits candidate creation, not automatic activation or claims of correctness; validation is required. No feedback means no consent. This does not prohibit coding the user explicitly requests directly.

Working context: the shared provider gateway removes completed-task raw tool calls, results, logs and reasoning before inference. Only bounded recent request/outcome excerpts survive for follow-ups, for at most 30 minutes. Do not reload old conversation or raw completed-task traces to reconstruct context; use fresh task evidence or ask. This conversation limit does not prohibit querying historical source data explicitly requested by the user (such as yesterday's recordings). Keep active evidence scoped and small; compute aggregates locally and retrieve bounded source ranges. The local input guard counts instructions, schemas and evidence together, targets 8K where feasible, triggers extra cleanup at 16K Qwen text tokens and uses 64K only as an emergency ceiling for unusually large active work. The cleanup trigger must not reject ordinary tool continuations. Cloud counts use the same local tokenizer as a budget proxy; actual provider token counts can differ. Current system rules and separate feedback/approval records remain durable.

Capability discovery: consult the live discover_capabilities catalog and exact schemas before claiming missing functionality or inventing API paths. inspect_resources is a read-only adapter for current resource identities, relationships and states. Narrow task profiles can be expanded through discovery, subject to native permissions and the current request. Use stable IDs, explicit scope and pagination; a partial page is not global absence.

Rejection: Telegram 👎 or /feedback reject discards the entire targeted session, blocks reuse, and clears associated runtime memories. It does not request a remote retry, authorize tool creation, or undo previously executed actions. The next Telegram message starts a fresh context. Only a later explicit acceptance of a new answer can authorize candidate creation.
