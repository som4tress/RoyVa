# Agent Learning — local components

Current implemented component: human feedback and candidate-creation authorization. The learning engine/tool builder is not implemented or installed yet; research into AutoSkill/WikiSkill/Hermes preceded this component. No program or skill is generated by the feedback command itself.

## Consent rule

No user confirmation means no permission to draft/build a candidate. `/feedback accept`, Telegram's `👍 Accept & learn` button, a standalone thumbs-up message, or an authenticated delivered thumbs-up reaction confirms the specific answer and grants candidate-creation permission. No second allow-build command is required. `/feedback reject <reason>`, thumbs-down or removing a thumbs-up withdraws permission. Acceptance is not proof of correctness or permission for automatic activation; candidates still need validation.

Defaults refer to the latest completed answer, never a pending tool call. Use `/feedback accept --message msg_ID` for a specific older OpenCode answer, or reply to its Telegram message. `/feedback status` shows current acceptance and consent. All receipt/recording paths avoid model calls.

## Components

- `src/feedback.mjs`: portable event store, exact response digest binding, consent state, emoji/command parsing, Telegram mapping. Node built-ins only.
- Deployment adapter: `~/.config/opencode/plugins/user-feedback/` registers one native OpenCode command for all server frontends. Uses the session-shell API only to print a static acknowledgment, with shell quoting. It does not send a prompt to a model.
- Telegram adapter: existing bridge routes feedback outside the task queue, retains durable bot-message-to-OpenCode-answer mappings, adds inline buttons and subscribes to reaction/callback updates. Existing allowlist enforced. Anonymous reactions are ignored.
- Future learning/runtime/MCP modules must check the consent ledger before any candidate generation. They must bind artifacts to the exact confirmed answer and recheck withdrawal before activation.

Data defaults to `~/.local/share/agent-learning/` (private directories/files). Override `AGENT_LEARNING_HOME` for tests. Store keeps IDs/digests and bounded feedback notes, not answer bodies or credentials. Command-source actor is the authenticated shared OpenCode user; Telegram includes the allowlisted user ID. This is not cryptographic user attestation against processes with the same filesystem/API access.

## Validation

Run `node --test test/*.test.mjs`. Integration evidence is in `~/llm-server/feedback-20261103/`: native command exercised accept/status/reject with zero new assistant messages, Shellular ACP status exercised without inference, actual Telegram reply delivery mapped to its exact assistant ID, and synthetic authorized/unauthorized reaction-handler tests verified grant/withdrawal. Native Telegram reaction delivery itself depends on Telegram's chat/admin restrictions; inline thumbs buttons and text commands provide an alternative. No physical device or reusable tool was created in testing. Test authorizations were withdrawn.
